# ADR-0008: Authentication, Sessions and Administrator Keys

**Status:** Accepted
**Date:** 2026-11-20
**Requirements:** FR-1.1, FR-7.1 to FR-7.4, NFR-API-5, NFR-SEC-4, NFR-SEC-7, NFR-SEC-9, A-1, SRS §4.6

## Context

Users call the API from untrusted devices (A-1), so identity must come from a server-verified credential, never a supplied user ID. NFR-SEC-4 requires Argon2id (≥ 19 MiB, t ≥ 2, p ≥ 1) for passwords and SHA-256 for high-entropy tokens and admin keys. §4.6 requires opaque session tokens with ≥ 256 bits of entropy, stored only as hashes, and admin keys provisioned outside registration with principal IDs that survive rotation. NFR-SEC-9 requires bounded throttling counters ([[resources/argon2id-password-hashing-and-session-tokens]], [[areas/authentication-sessions]]).

## Decision

* **Passwords:** BouncyCastle Argon2id, 16-byte random salt, 32-byte output, encoded as `$argon2id$v=19$m=<kib>,t=<n>,p=<n>$<salt>$<hash>`. Defaults are the SRS minimum and configurable upward (`LEDGER_ARGON2_*`). Verification uses constant-time comparison. An unknown login still verifies against a dummy hash to equalize timing.
* **Sessions:** `POST /auth/login` returns `accessToken` = 32 bytes from `SecureRandom`, base64url without padding. The `user_session` row stores `sha256(token)`, `expires_at` (default 60 minutes, `LEDGER_SESSION_LIFETIME_MINUTES`) and nullable `revoked_at`. Logout revokes one session; logout-all revokes every active session of the user. Revoked or expired → `401 UNAUTHENTICATED`.
* **Admin keys:** `LEDGER_ADMIN_KEYS="ops=<sha256hex>,backup=<sha256hex>"`. The raw key (≥ 256 random bits, generated by the operator) is sent as `X-API-Key`; the server hashes it and compares against every configured hash in constant time. The matched `principalId` becomes `admin:<principalId>`.
* **Authorization:** USER on `/admin/*` → 403. A user may read only their own user and wallets, create wallets only for themselves, debit only their own wallet, and read a transaction only if one entry is on their wallet. ADMIN may read any resource and create a wallet for an existing user, but may not call `/auth/logout*` or `POST /transfers` (403). Recipient wallet existence and currency are checked without revealing its owner or balance.
* **Throttling:** in-memory sliding-window counters keyed by login name (5 failures / 15 min), source IP (20 failures / 15 min) and registration IP (10 requests / 15 min), bounded by an LRU cap. Exceeded → `429 TOO_MANY_REQUESTS` with `Retry-After`. `X-Forwarded-For` is honoured only from `LEDGER_TRUSTED_PROXIES`.
* **Transport:** default listen address `127.0.0.1`; non-loopback deployment must sit behind TLS 1.2+ (documented in the user guide). Secrets never appear in URLs.

## Alternatives Considered

| Option | Why not chosen |
|--------|----------------|
| JWT access tokens | Cannot be revoked instantly without a server-side list; FR-7.3 requires immediate revocation. |
| bcrypt / PBKDF2 | Not memory-hard; NFR-SEC-4 names Argon2id. |
| Admin accounts in the database | Registration must never create admins (FR-1.1); configuration keeps provisioning out of band. |
| Persistent throttle counters | Not required; in-memory counters reset on restart, which is acceptable for a single-process service. |

## Consequences

* Argon2id at 19 MiB costs tens of milliseconds per login; login is excluded from the transfer latency target.
* Tests use reduced Argon2 settings only through the `PasswordHasher` provider in unit tests; system tests use real settings.
* Tests: generic 401 for unknown login and wrong password, expiry with `FixedClock`, single and all-session revocation, cross-user 403s, admin/user separation, throttle 429s with `Retry-After`, trusted-proxy handling.
